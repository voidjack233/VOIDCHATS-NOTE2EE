# Image-history signing audit

Baseline: `fb8a4414281b8b3e12db9959427f22515f2ac30f`. Measured 2026-09-25
with Node v24.13.1 on the shared development host. This is not a production
load test. Only one production file changes: `server/vmd/capability.ts`.

## CURRENT SIGNING FLOW

HTTP cookie/session authentication -> history fetch limiter -> conversation
identity/storage resolution -> membership -> Sentinel-coalesced Scylla history
-> user-specific reactions -> batch attachment lookup scoped by conversation and
bucket -> finalized blob policy -> original MinIO presign -> VMD variants ->
descriptor mapping and JSON response. Authorization still runs per request.

The mapper deduplicates attachment IDs before both metadata lookup and delivery
generation, and retains its existing bounded concurrency. Finalized blob rows
avoid MinIO stat. Legacy/incomplete rows retain the independent metadata check.
VMD requires an eligible descriptor AND trusted original delivery `inline === true`.

## ORIGINAL DELIVERY

Original signing cannot simply disappear: fallback must work immediately when
VMD fails or cannot render an otherwise supported original (for example an
animated source). Web download selects the original URL; native also uses it
directly. `resolveAttachmentBlob` can download it, then try the authenticated
stable fallback. The protected GET endpoint streams bytes after membership and
object checks; it is not an existing lazy signed-URL resolver.

Lazy original delivery would require new request/retry contracts across web and
native. That scope and fallback regression risk are not justified here. All 20
original presigns remain on a 20-unique-image page.

## VMD VARIANTS

Timeline uses small/medium with responsive sizes. Viewer uses medium/large with
`90vw`. Large is interaction-only but removing it requires viewer recovery/API
changes. The original is fallback/download-only on the normal VMD success path,
but must already be available when that path fails. All three variants remain.
Medium's display alias adds JSON bytes, not another signature.

## KEY DERIVATION

The existing domain-separated HMAC derives solely from
`VMD_SIGNING_SECRET || ACCESS_SECRET` and `void:vmd:capability-signing-key:v1`.
There is no user, conversation, attachment, variant, expiry, or request salt in
this derivation. Baseline performs it three times per responsive image.

Chosen optimization: derive once inside a synchronous responsive-delivery call
and pass the result to all three variants. No process-global cache, no stored
key, no cross-request reuse. The next call re-reads configuration. Explicit
caller keys still take precedence; invalid configuration still fails closed.
The exported key function still returns a fresh buffer, avoiding caller mutation
of cached key material. Tests cover rotation, ACCESS_SECRET fallback, mutation,
explicit keys, exact URLs, and missing/invalid secrets.

## MINIO SIGNING

`server/minio.ts` configures static credentials and an explicit region. In SDK
8.0.7, `getBucketRegionAsync` returns that region without I/O and
`checkAndRefreshCreds` does nothing without a credentials provider. The SDK then
normalizes response parameters, escapes/sorts the canonical request, hashes it,
derives its SigV4 key with four HMACs and signs with a fifth HMAC. One SHA-256
canonical-request hash is also required per presign.

The compiled-service probe counted zero CDN transport requests during signing,
and zero object stats for the finalized fixtures in every measured batch.
CPU samples do show SDK work: roughly 0.95 ms per 20-image page attributed to
`presignSignatureV4` and descendants in the two baseline profiles. URL/canonical
construction, date formatting, encoding, HMAC initialization/update/digest are
visible. This is meaningful but does not justify replacing the SDK. Async
per-presign wall spans overlap and must NOT be summed and called signing CPU.

## DUPLICATE WORK

Twenty references to five attachment IDs produce five original presigns and
15 capability signatures, not 20/60. Baseline key derivations are 15; candidate
derivations are five. Duplicate signing was already absent within a page.

## CROSS-REQUEST REUSE

VMD URLs are deterministic for attachment + variant + expiry bucket + key +
origin. Default five-minute expiry buckets and the one-hour ceiling are unchanged.
Original SigV4 uses current time to second precision, not the VMD bucket: same
second and same signing inputs can produce the same URL, different seconds do
not. Original expiry metadata also has its existing independent clock timing.

Pure-signing reuse could theoretically follow fresh authorization, but would
need bounded lifetime/size, complete key/policy/object/filename identity, rotation
handling, and no extension of URL expiry. It must never cache membership or
inline approval. No such cache is implemented or claimed proven safe here.
Sentinel still coalesces in-flight history reads only, not completed deliveries.

## NATIVE BENCHMARK

`scripts/benchmark-native-history.mjs` builds the exact baseline with tsc in a
private directory, and builds a candidate differing only in `capability.ts`.
It forks the real `dist/server/entrypoints/message-server.js` with its normal
middleware, auth, startup schema checks, pools, SDK, and routes. No VM handlers
are used in the measured server. The separate benchmark client imports fixture
helpers only to provision isolated stores and synthetic data.

PostgreSQL/Valkey/MinIO are disposable, non-production instances. Scylla uses one
random temporary RF=1 keyspace, dropped after the run. Both builds share exactly
the same seeded messages, objects, credentials, and service settings. Default
PG pool max remains ten. Canonical blob keys and trusted finalized metadata are
seeded alongside actual JPEG bytes; original URLs are fetched successfully from
the isolated MinIO server, not merely checked for URL shape.

Run order is baseline, candidate, candidate, baseline (ABBA). Per process/scenario:
10 excluded warmups; separate crypto-count request; 50 sequential measured
requests; for 20 images, five waves each at concurrency 10/50/100. Counts are
instrumented separately from timings. Each process then profiles 200 additional
sequential image requests, excluded from the latency comparison. No test suite
ran during measurements. HTTP assertions/client parsing run outside the service.

Initial native baseline before the code edit:
`benchmark-results/native-history-2026-09-25T02-21-16.811Z.json`.
Matched comparison:
`benchmark-results/native-history-2026-09-25T02-23-03.674Z.json`.
Four sibling `-<round>-<label>.cpuprofile` files contain actual service profiles.
Both runs completed with zero cleanup errors; no production rows were touched.

## CONFIRMED BOTTLENECK

Native sequential image history remains more expensive than text. Baseline VMD
generation is about 1.27 ms/page, not the VM harness's approximate 3 ms/page.
Local signing is measurable; it is not the only cause of high-concurrency delay.
Under concurrency 100 the event loop remains approximately 99.7% utilized.
This is a small CPU reduction, not a saturation or end-to-end performance cure.

## CHANGES MADE

Only call-local VMD key reuse is applied to production. No capability fields,
signature payloads, expiry calculations, original presigning, frontend code,
authorization, sanitizer rules, SQL queries, pool settings, or deployment change.

## SECURITY

No authorization cache or new trust path. Each history still authenticates and
checks membership; attachment lookup remains conversation/bucket scoped. Exact
inline approval, VMD storage trust checks, MIME policy, capability verification,
expiry boundaries, secret rotation, and original SDK signing remain intact.
Invalid/foreign IDs retain protected fallback behavior. This is isolated testing,
not a deployed penetration test.

## FRONTEND COMPATIBILITY

Byte-identical VMD output for fixed inputs preserves CDN keys. All existing URL
fields and original fallbacks remain available. Cached message delivery refresh
still merges refreshed metadata into IndexedDB; runtime patches cannot reinsert
trimmed messages. Forwarding/edit serialization still strips transient URLs in
favor of stable attachment identity. Loaded-image retention, native image tags,
viewer medium/large selection and original download selection are unchanged.
